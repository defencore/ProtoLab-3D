# Structural parts organization audit

Historical section review, 2026-11-03, before curator integration. Some recommendations below were implemented in the same organization pass; use the [integrated review](../library-organization-audit.md) for completed changes and remaining work. Runtime counts describe that review snapshot. Raw snapshots and logs are optional local evidence under ignored `test-results/`; this document preserves the section findings in the repository.

Scope: all 20 current `STRUCTURAL PARTS` packages (current runtime inventory in `before.json`). This is a source and metadata audit; no native geometry was generated and no strength or manufacturing qualification is claimed. Source code was not changed.

## Immediate safe organization changes

1. Add the two shared catalogs above in `src/core/library.ts`: `['aluminium-profile', 'slot-profile']` and `['wheel', 'robot-wheel']`. Their category/subgroup paths already agree. This reduces 20 structural browse rows to 18 without changing any physical component or configured parameter.
2. Preserve every existing package and preset ID. No duplicate package IDs or duplicate local preset IDs were found in the structural inventory. Runtime catalog-generated servo-bracket presets must be checked through registration rather than its empty source `presets.json` alone.
3. Improve visible preset titles without changing source designations: `wheel` should identify diameter (`Utility wheel · Ø35 mm`, etc.); `cnc-spindle-mount` should use `Ø65 mm · Rear block` rather than `65 mm / Rear block`; `l-bracket` can expose actual envelope dimensions rather than only Small/General/Large. Keep selector and preset titles synchronized.
4. Source-independent engineering placeholders should use useful functional browse labels and descriptions; do not rename all generic recipe definitions to “Bracket” or expose backend mesh controls as product choices.
5. Add `GUIDE.md` source/fidelity notes for `metal-servo-bracket` (currently absent). Its identity and native source records already live under `lib/`; source registration is not evidence that all interface dimensions have been reviewed.

## State/schema issues requiring affected validation

- `structural-section`, `slot-profile`, `sheet-bracket` and `din-rail` each emit exactly one piece in `lib/model.ts`, yet declare both `assembled` and `exploded`. `finish()` in `src/core/assembly/mechanical/helpers.ts:110` returns a single piece unchanged. Their exploded states are therefore identical and conflict with the meaningful-state rule. Remove them from available UI choices while preserving the canonical physical state and saved state semantics through the shared state reconciliation contract. Check package validation, configuration persistence and export after this change.
- `cable-carrier` emits one piece for duct, many for chain; use `states[].availableWhen` for exploded. `machine-hardware` handle and cap likewise have one body while hinge/latch/foot have several. Model-state availability should follow actual separability rather than the presence of a generic factory.
- Generic recipe definitions have no model presets and rely on structured text supplied by assemblies. A project should not acquire an arbitrary “supplier” identity by browsing an editable installation envelope. Keep production/release requirements explicit.

## Evidence and checks

Reviewed runtime metadata plus `part.ts`, `configurator.ts`, `presets.json`, `product.json`, relevant `GUIDE.md`, and `lib/model.ts`/geometry helpers for the overlapping groups. A local JSON inspection found no duplicate literal preset IDs or titles across each package's own file; runtime counts include catalog-derived records. No tests, package checker or FreeCAD execution were run by this analyst. Recommended integration checks: library catalog membership, exact IDs and search, product library views, state selection, physical composition, and affected package checks; native geometry verification is required if geometry engines are merged.
