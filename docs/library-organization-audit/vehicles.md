# Vehicle structures organization audit

Historical section review, 2026-11-03, before curator integration. Some recommendations below were implemented in the same organization pass; use the [integrated review](../library-organization-audit.md) for completed changes and remaining work. Runtime counts describe that review snapshot. Raw snapshots and logs are optional local evidence under ignored `test-results/`; this document preserves the section findings in the repository.

Scope: all 40 current `VEHICLE STRUCTURES` physical packages, 361 runtime presets and 38 initial navigation entries. Read-only source and metadata inspection; no source files were modified. Root is library curator.

## Immediate safe naming changes

1. Add concise sentence-case browse labels without changing configuration/physical identity: `rocket-airbrakes` → **Rocket airbrake**; `rocket-release` → **Rocket release mechanism**; `clamp-band-release` → **Clamp-band separation mechanism**; `rocket-parachute-recovery` → **Parachute recovery assembly**; `rocket-co2-recovery` → **CO₂ parachute recovery assembly**; `rov-component` → **ROV fabrication detail**. Current uppercase/camel-case AirBrakes/Mechanism/Assembly titles are inconsistent with the rest of the tree.
2. Normalize authored dimensional preset titles: nose `D54 x 150 mm` → `Ø54 × 150 mm`; sled `40 x 120 x 2.5 mm` → `40 × 120 × 2.5 mm`; rail button `D10 × 9.7` → `Ø10 × 9.7 mm`; transition `D54 / D75 x 90 mm` → `Ø54 → Ø75 mm · 90 mm long`. Use distinct labels for OD/ID where a slash could be mistaken for another execution. Preserve original supplier designations, source titles and source CAD labels.
3. Separate evidence limitations such as `prototype`/`reference` from component-type navigation. The existing evidence/profile already supplies this information; do not delete it from descriptions. In camera-nose titles retain the actual camera execution and packaging distinction, while standardizing dimensional separators and units. Do not replace the literal OV9281-110 designation or infer that all 19 mm CSI cameras are the same product.
4. Source ROV detail names currently preserve title/case such as `Pressure Sensor Mount` and `Cable passing Screw`; curated selector titles can use sentence case while source-native labels remain evidence. Keep preset and component-selector names synchronized.

## Grouping and parameter decisions

The existing Rocket nose cone family is the requested behavior for camera variants. `rocket-camera-nose.cameraSetup` selects the 19 mm CSI cartridge, OV9281-110 cartridge or dual installation; `packaging` selects structural-ogive/TPU/tandem/sandwich arrangements. `availableWhen`, `updateParameters` and validation constrain supported combinations. Those variants should not become new navigation entries or interchangeable unsourced camera dimensions. `rocket-nose-cone` remains a separate simple body definition under the same chooser, with independent origin, geometry and production profile.

Model rockets currently has 23 physical packages and 22 browse entries. It is the busiest subgroup, but the entries describe genuinely different functions; merging them all into a generic rocket component geometry API would obscure datums and physical identity. If browsing becomes unwieldy, evaluate sibling functional subgroups (airframes/body parts, recovery/separation, mounting/guides) with user navigation evidence and coherent taxonomy updates. Do not introduce a supplier or size folder layer. No additional shared catalog is necessary in this pass beyond existing nose and multicopter groups.

`rover-chassis` fixed supplier models preserve revision differences. The DFRobot CAD does not match every current dimension statement and must not be resized. `multicopter-frame` retains pinned source frames/licenses and per-source sheet/print availability. `rov-project` records source BOM gaps and canonical purchased units. Similar appearance or matching mounting dimensions do not justify deleting any of these source identities.

## State/schema follow-up

- `propeller/lib/model.ts` adds exactly one fused Rotor and `duct/lib/model.ts` one Duct. Both call `finish(out,state)`, whose shared implementation returns unchanged pieces when count < 2. Their advertised Exploded states are therefore no-ops. Review removing/unavailable choices through saved-state reconciliation; do not split a one-piece rotor merely to create an exploded view.
- `landing-gear` genuinely has tyre/hub/fork/axle/retainers/strut components; retain meaningful inspection separation. Camera-nose service and print-layout states also represent explicit geometry/export arrangements rather than camera product variants.
- Canonical state labels vary (Assembly, Supplier assembly, Mechanical assembly, Installed assembly). A future state-label cleanup can consistently use Assembled with the scope in descriptions, while preserving state IDs and physical/BOM behavior.
- Profile/section sampling resolution fields and hidden component recipes are engineering controls. Keep them distinct from product/model choices; an organization cleanup must not silently alter native topology or source geometry.

## Checks and limits

A local JSON scan found no duplicate local preset IDs or titles in any of the 40 packages. Package IDs match their current folders on inspection. No ID rename is justified. Preserve each qualified `<part.id>:<preset.id>`, source revision/license and physical composition. The three fixed source vehicle families and their reusable components are not opaque substitute meshes.

No package, geometry, CAD export, source-dimension or engineering readiness checks were run by this analyst. Any state or geometry consolidation requires the affected package/identity/composition/export verification.
